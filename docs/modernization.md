# Modernization — 2026-09-11

## Scope and upstream comparison

Base: `b06262b894bf7526b4395096e45c9dc2c2c9b78d` in the existing fork.
Upstream compared: `6991c94` from hemanthrajv/flutter_compass master, fetched
2026-09-11 (package 0.8.1). Changes are selective, not a rebase.

- Adopted upstream's same-instance Android engine registration and detach
  cleanup, plus its empty web stream behavior.
- Fixed the documented missing-sensor event and avoided registering unused
  fallback sensors when the rotation-vector sensor is present.
- Retained Android's existing azimuth range, camera placeholder, accuracy
  estimates, filtering, and orientation calculations. Invalid fallback rotation
  matrices are no longer emitted as headings.
- Preserved the Swift implementation from fork commit `e4df9e3e` byte for byte.
  It moved into the standard SwiftPM Sources directory shared with CocoaPods.
  Flutter registers the existing Swift class directly instead of using the
  Objective-C forwarding class.
- Did not take upstream's iOS true-north/statusBarOrientation changes: they
  would change this fork's public heading semantics and use a deprecated API.
- Updated the example's Gradle plugin loader, Java toolchain, Android manifest,
  CocoaPods helper, Flutter text styles, and iOS UIScene integration. The latter
  was generated by Flutter's standard project migration during the build.
- Removed unused example cupertino_icons; moved flutter_compass to runtime
  dependencies and updated permission_handler from 6.x to 12.0.3. Version 13.x
  requires SDK 37 and is outside this SDK 36 validation scope.

The Flutter floor is 3.44, which introduced AGP 9 compatibility. The example
uses built-in Kotlin (Flutter 3.47+) with Kotlin 2.4.20. Plugin iOS and Android
OS floors remain 14.0 and 21; current Flutter can impose higher host floors.
No claim is made that every version above the declared floor has been tested.

## Consumer integration

The app's existing Kotlin 2.4.20 / AGP 9.1.0 / Gradle 9.3.1 migration was tested
with this fork on Flutter 3.47.2. Android alpha debug APK and iOS alpha simulator
Runner both build. An isolated iOS simulator also reaches `app.started` and
`ready=true`; this proves startup, not compass sensor functionality. The app's
redundant compass namespace workaround was removed.
The dependency and pod lock changes are scoped to flutter_compass.

Full alpha release is blocked after the compass configuration fix, at
`:clipboard:checkReleaseAarMetadata`: the unrelated clipboard plugin compiles
against SDK 33 but its resolved AndroidX dependencies require at least SDK 34.
No clipboard/cache patch or disabled metadata check was used. Consequently the
full app's release/R8 gate is **not green**. The example release APK does pass.
The consumer release attempt excluded only its Crashlytics mapping upload task.

The app/server migration remains separate work with uncommitted changes; these
local build results do not constitute CI or approval to merge either PR.

## Required physical iOS check

1. Launch the example on a compass-capable iPhone and allow any foreground
   permission requested by the example. Rotate it and confirm magnetic heading
   and camera-mode heading change plausibly.
2. Instrument `onListen` and `onCancel` using Xcode breakpoints. Verify motion
   updates do not start at plugin registration.
3. Cancel the last Dart listener and confirm `stopUpdatingHeading` and
   `stopDeviceMotionUpdates` are called. Subscribe again and confirm readings.
4. In the consuming app, background the compass UI and confirm its lifecycle
   cancels the last subscription; verify motion is stopped. Resume and verify
   resubscription. Keeping a live listener while backgrounded is not covered by
   the original cancellation-driven fix.
5. Check calibration, portrait/landscape, screen lock/unlock, and camera mode on
   physical hardware. Do not treat simulator compilation as evidence for these.

The durable Android sensor check runs from the example:

```sh
fvm flutter test integration_test/compass_test.dart -d <physical-device-id>
```
